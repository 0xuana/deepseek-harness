# Agent Note: 在步骤准备之前选定步骤模型

Status: implemented

[English](2026-10-12-step-model-chosen-before-preparation.md) | 中文

## 问题

工具是否可用可能取决于声明这些工具的请求所用的路由：`web_search` 不得出现在没有搜索凭据的路由上，计划或团队状态也可能撤下其他工具。消息准备同样需要这一模型：会话引用按模型的上下文窗口确定快照大小，模型选择会通告模型切换。循环原先在 `agent/pre-step` 之前组装工具与提示词段落，直到 `step/start` 之后才在 `agent/request` 中决定提供方、模型与推理强度，因此更早的消费方只能依据模型选择状态预测它们。若监听器在 `agent/request` 中（包括在重试时）替换它们，已组装的提示词与工具目录就会描述另一个模型。计划状态也有同样的问题：它在 `agent/pre-step` 内提交，计划指引只能依据待提交的选择预测。

## 决策

提供方、模型与推理强度是步骤级事实，像用户在发送消息前那样一起选定。领取输入之后，循环派发串行事件 `agent/step-boundary`，插件在此提交从本步骤起生效的选择，例如待提交的计划模式切换。随后循环为每个拟议步骤派发一次 `agent/model`。其默认值在本循环记录请求之前取自 agent 选项，之后取自已记录的请求头，且只有为该确切模型选定过的推理强度才会保留；`installModelSelection` 在这里返回其当前选择。循环把结果发布为 `agent.step`，并在步骤结束或提案被拒绝、失败、取消时清除。`agent/pre-step` 监听器、工具条件、提示词段落以及 `{{provider}}` 与 `{{model}}` 变量都从 agent 读取该选择。

`agent/pre-step` 接纳步骤且 `step/start` 打开步骤之后，循环解析条件工具并一次性组装提示词：段落、变量、运行时上下文与工具声明。运行时上下文快照在该步骤已接纳的消息之后提交。之后每次请求尝试都在准入之前紧接着运行 `agent/request` 与 `prepareCall()`。`agent/request` 可以修改采样控制参数；返回其他提供方、模型或推理强度会使步骤失败。重试复用该步骤的模型选择、工具集合与已渲染组装结果，步骤拥有的工具集合在该步骤的工具批次结束后关闭。步骤进行中做出的选择从下一个步骤开始生效。

## 考虑过的替代方案

- **在 `agent/pre-step` 之前通过 `agent/request` 绑定路由，并提供 `Agent.currentRoute()`。** 已准备调用会捕获适配器注册与连接设置，因此在压缩、钩子与会话读取期间一直持有它，会忽略期间修改的设置；被 `agent/pre-step` 拒绝的步骤也会准备适配器。该 getter 只在步骤内有效、在其他时刻抛错，且每个 Agent 实现与测试替身都必须提供它。
- **在 `agent/pre-step` 内选定模型。** pre-step 监听器自身就要用模型计算引用预算和切换通告。在同一个 waterfall 中既决定又使用模型，每个监听器看到的值就取决于注册顺序。
- **把选择作为参数传给每个消费方。** `AssembleContext`、pre-step payload 与 `ToolActivationContext` 各需一个字段，之后每增加一项步骤决定都要同时改这三处。`agent.step` 为它们提供单一来源。
- **不使用事件，直接在 Agent 上登记模型选择。** 这会给通用 `Agent` 接口增加只有单一消费方的方法，并移除为创建时没有模型的 agent 提供模型的监听器途径。
- **决定留在 `agent/request`，为更早的消费方预测它。** 只要模型选择之外的监听器修改模型，预测就会偏离。
- **每个步骤只选定提供方与模型，推理强度留给 `agent/request`。** 推理强度只对选定它的模型有效。拆开后，`installModelSelection` 必须在一个 waterfall 中捕获选择，再在另一个 waterfall 中、且仅当其他监听器没有替换模型时应用推理强度；重试也可以在步骤内修改推理强度。
- **在 `agent/pre-step` 之前用单独的 `system-prompt/prepare` 阶段准备运行时上下文。** 它把运行时上下文保留在已领取输入与 pre-step 监听器追加的消息之间，但把组装拆成了两个钩子，并让仅运行时上下文变化就能打开一个步骤。
- **在 `agent/pre-step` 内提交待生效的计划选择。** 提交之前运行的阶段和监听器看到的是旧的计划状态，模型选择也无法依据计划模式。

## 后果

- 工具条件、提示词变量、引用预算与切换通告读取的提供方与模型，与请求头记录的一致。
- `prepareCall()` 紧邻分发，因此其适配器注册与连接快照只覆盖请求头记录与流式请求。
- 步骤无法在重试时切换到其他提供方或修改推理强度；需要这种能力的策略必须为重试的尝试重新执行模型选择、工具解析与组装。
- `agent.step` 在两个步骤之间以及 `agent/model` 期间为 undefined；跨步骤运行的工作要在开始时读取它。
- `agent/model` 监听器可以读取计划状态，因为步骤边界会先提交它；但模型选择仍不能依赖 `agent/pre-step` 的结果。
- 即使 `agent/pre-step` 拒绝了该步骤，待生效的计划模式选择也已提交；其通告会出现在下一个被接纳的步骤中。
- 运行时上下文快照位于该步骤已接纳的消息之后，仅运行时上下文变化不会打开步骤。
