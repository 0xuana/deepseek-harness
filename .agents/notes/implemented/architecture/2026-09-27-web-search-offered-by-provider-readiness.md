# Agent Note: Offer web_search and web_fetch only while the selected provider is ready

Status: implemented

English | [中文](2026-09-27-web-search-offered-by-provider-readiness.zh.md)

## Problem

`dsh-tool-web` registers `web_search` whenever search is enabled, and the [web capability seam decision](2026-06-24-web-capability-seam.md) keeps it visible while the selected provider cannot run. The shipped search provider, `dsh-web-search-deepseek`, authenticates a search with the DeepSeek account token only for a model request on the `deepseek-account` route; every other route needs a configured API key. A Session on an API-key route without a search key was therefore offered a tool whose every call failed with `WEB_PROVIDER_CREDENTIAL_MISSING`, and a conversation on another provider's model searched with `DEEPSEEK_API_KEY` whenever it was set, billing DeepSeek for searches the user had not chosen. Sessions in one Host can use different routes, a Session can switch routes between requests, and the Web app registers `web_search` once per agent preset, so no registration decision matches every request. The Search and Fetch APIs of `dsh-web-deepseek-api`, which the Web search settings switch selects together, need that credential for both operations, so the same Session was also offered a `web_fetch` whose every call failed.

## Decision

Each role of the web capability seam owns one part of a per-step check:

- **Service Definition.** `WebSearchProvider` and `WebFetchProvider` have an optional `ready(llmProvider)` that answers whether an operation made for a model request on that chat route has a credential to send. It checks configuration only and makes no network calls. `ctx.web.searchReady(llmProvider?)` and `ctx.web.fetchReady(llmProvider?)` resolve the provider with the same rules as `search()` and `fetch()` and return its answer. A provider without `ready()` counts as ready, and a selection failure answers true because the operation reports that failure as a structured `WebError`.
- **Service Provider.** `dsh-web-search-deepseek` answers true for a model request on the `deepseek-account` or `deepseek-official` route, or on another route when search has a key of its own, and then when the route is `deepseek-account` and `ctx.deepseekAccount.resolveToken()` returns a token for the configured search endpoint, when the section carries a literal `apiKey`, or when `ctx.credentials.describe()` reports the `apiKeyEnv` reference configured (without that service, when the launching environment carries it). It checks credentials in the order `search()` resolves them, and a failed account-token or credential-store read answers false, because `search()` fails on that read instead of trying the next credential. The Search and Fetch API providers of `dsh-web-deepseek-api` share one credential and answer the same way for their API base; their transport repeats these checks, so neither package depends on the other. The providers name no tool or prompt section.
- **Consumer.** `dsh-tool-web` registers `web_search` and `web_fetch` with [step activation conditions](../../../../packages/core/tools/README.md#conditional-tools) that ask `ctx.web.searchReady()` and `ctx.web.fetchReady()` about the route of the step's model selection. The agent loop resolves conditions before it assembles the step, so the declared tools, the `tool:web_search` and `tool:web_fetch` prompt sections, PTC program bindings, and dispatch all read the same admitted set.

Without a key of their own, the DeepSeek providers serve only the two DeepSeek routes, because another provider's conversation would otherwise bill the shared DeepSeek key for searches the user did not choose. A key of the provider's own, a literal `apiKey` or an `apiKeyEnv` other than `DEEPSEEK_API_KEY`, opens every route, since the user chose what that key pays for; an endpoint setting does not, because the search still sends the shared key. Each provider repeats the route check in its API-key resolver, the only place the key leaves, so a direct `ctx.web.search()` or `ctx.web.fetch()` for such a conversation fails with `WEB_PROVIDER_ROUTE_DISABLED` before any credential is read. The providers do not compare the chat route's endpoint with their own: when the official route chats through a gateway, the tools stay offered and each operation sends the configured key to the configured endpoint.

Only presence decides: no API key value is read and no endpoint is contacted, so a wrong key or an endpoint that does not serve the native `web_search_20250305` server tool keeps the tool admitted. A step that does not admit a web tool also refuses calls to it as `UNKNOWN_TOOL`, so a model that repeats an earlier call reaches no provider; an operation made outside a model step still applies the provider's checks when it resolves the key.

The request header records the assembled tools, so the agent loop announces each change through tool-registry updates. A route switch, a stored key, or a removed key changes the next request; DeepSeek routes load a returning tool as a deferred addition, and routes without tool-update support receive the complete tool list.

## Alternatives considered

**Let the DeepSeek provider remove `web_search` in its own assemble listener.** The seam stays unchanged, but the provider then names another package's tool, prompt section, and PTC transport, and it removes the tool even when the deployment selects another search provider, such as Exa, whose searches would succeed.

**Extend `available()`.** It is synchronous and takes no request, while this check reads an asynchronous credential store and depends on the request's route. A route-dependent `available()` would also make provider selection depend on the conversation.

**Read the route from the Session's latest `request/context` event instead of passing it.** That event records the previous request, so a new Session's first request and the first request after a model switch would be decided for the wrong route or for none.

**Register or unregister `web_search` in `dsh-tool-web`.** Registration is shared by every Session of an agent preset, while credentials depend on each request's route. Unregistering would also make `toolOrder` entries and subagent `toolFilter` restrictions that name `web_search` fail.

**Remove `web_search` from the assembled request.** A `system-prompt/assemble` listener could drop the declaration and its section, but the tool would stay executable, so a model that repeats an earlier call would still run it, and PTC programs would still bind it. Prompt assembly also no longer carries tool declarations.

**Offer search only on the DeepSeek account route.** Account tokens are issued only for the official endpoint, so a gateway key could never reach DeepSeek. But every shipped profile defaults to the `deepseek-official` route, so search would be off by default, including the official API-key case.

**Keep offering search on every route that has a DeepSeek key.** A conversation on another provider's model would bill DeepSeek for each search without the user choosing it.

**Serve only the DeepSeek routes, whatever key the provider has.** One rule would cover every configuration, but a user who gives search a key of its own has chosen what that key pays for, and could not use DeepSeek search from other models at all.

**Open other routes for a configured endpoint too.** A `baseURL` or `$DEEPSEEK_SEARCH_BASE_URL` also marks search as set up deliberately, but the search would still send the shared DeepSeek key, and changing an address on the Web search settings page would silently open every model.

**List the routes that may search.** A `routes` setting would state the intent directly, but a key of search's own already states it, and a second setting is one more thing a user has to find.

**Send the chat key only to an endpoint on the official chat route's origin.** This keeps a gateway's key away from DeepSeek, but the providers would have to find the chat route's configuration themselves. Taking the first active `dsh-llm-deepseek-api-key` Loader row answers for an unrelated instance when a composition isolates several, which disables a correct route or lets a gateway key through; only the route's owner knows which endpoint serves a request, and an endpoint field in `dsh-llm` would reach the browser through the Remote `listProviders()`. Without the check, a gateway user's search fails at the configured endpoint.

**Keep the tool offered and fail at execution.** The model spends a call on a search that cannot authenticate, and the failure repeats on every attempt.

**Probe the key or endpoint before offering the tool.** A network request per model request adds latency and cost; the user controls configuration, not its validity at that moment.

## Consequences

`dsh-web` gains public members: the optional `ready()` of both provider interfaces, `WebRuntime.searchReady()`, and `WebRuntime.fetchReady()`. Each readiness method is the smallest query its one consumer needs, which is how the [observation-surface decision](../../archived/simplification/2026-07-04-drop-unconsumed-web-observation-surface.md) lets a status query return; neither reports availability or selection failures. The Exa, Perplexity, and HTTP fetch providers implement no `ready()`, so their behavior is unchanged, and `web_fetch` stays admitted whenever the switch leaves HTTP fetch selected. A step that does not admit a web tool leaves it out of PTC program bindings too. An endpoint that cannot serve the native server tool keeps the tool admitted and fails each call. Removing a tool on an unchanged route changes the declared tools and misses the prompt cache once; a model switch already invalidates it. Conversations on other providers' models get a DeepSeek web tool only when the provider has a key of its own; otherwise they need another search provider such as Exa or Perplexity, and with the Search and Fetch APIs selected they also lose `web_fetch`, which local HTTP fetch serves while the switch is off. The Web search settings page saves its key under `apiKeyEnv`, `DEEPSEEK_API_KEY` by default, which the chat route also reads, so a key saved there opens only the DeepSeek routes; a deployment that points `apiKeyEnv` at its own reference makes the page store a key of search's own. The [upgrade guide](../../../../docs/upgrade-guide/v0.2.1-rc.2/deepseek-web-tools-deepseek-routes/guide.md) gives the migration. A deployment whose official route chats through a gateway keeps the tools, and each search sends the configured key to the configured endpoint, the official one by default. The DeepSeek web packages read no Loader rows and depend on no LLM package.

Unit tests pin each role: `packages/web/web/tests/web.spec.ts` covers which provider `searchReady()` and `fetchReady()` ask and their answer on selection failure, `packages/web/web-search-deepseek/tests/deepseek.spec.ts` and `packages/web/web-deepseek-api/tests/readiness.spec.ts` cover each credential and route case of `ready()`, and `packages/web/tool-web/tests/tool-web.spec.ts` resolves step admission of both tools through the real prompt, tool, and executor services, including the `UNKNOWN_TOOL` refusal of a call in a step that withheld the tool. In real compositions, the shipped headless keyless smoke test, whose `cli-mock` route is not a DeepSeek route, and the `web-search-unconfigured` recorded-session snapshot, whose search key reference is unset, pin the withheld search tool. Snapshot replays supply a placeholder DeepSeek key, so their tool lists do not depend on the runner's environment, and the `pi-ai-conversation-updates` snapshot pins that a conversation on a pi-ai route is not offered `web_search`.
